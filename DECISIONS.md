# Decisions log

Design choices behind the server, the index generator and the benchmark. Each entry
states the decision and, briefly, why.

## Runtime and protocol

- **Python + uv**, official MCP Python SDK 2.x low-level `Server`, stdio only.
  The low-level API gives exact control over tool schemas (no `default` on
  `version`), annotations and single-text-content results.
- **Argument validation** uses strict Pydantic models with unknown arguments
  rejected (`extra="forbid"`), so an inapplicable argument is never silently
  ignored, and `5`, `true`, `"5"` etc. never coerce into a version.
- Nullable parameters are declared as `{"type": ["string", "null"]}`. Optional
  arguments accept the spellings agents actually send: null, blank text, or the
  words "null"/"none"/"undefined" mean "not given" (both the Copilot and Claude
  harnesses sent `"limit": "null"` in testing); `"3"` or `3.0` is accepted for an
  integer and `"true"`/`"false"` for a boolean. A bare number is accepted for the
  free-text `query`/`section`. `version` and range limits stay strict.
- Argument errors carry the `MQTT <version> only (...)` prefix whenever the
  `version` argument itself is valid. Any unexpected exception is caught and
  returned the same way as an internal-error tool result, so no unscoped error
  reaches the client.
- The server works with both the legacy `initialize` handshake and the
  2026-07-28 per-request protocol era; the SDK negotiates this.
- `MqttSpecService` is the transport-independent dispatcher. The test hook is
  `MqttSpecService(["5.0"])` / `create_server(["5.0"])`.

## Source pinning and canonicalization

Canonicalization (`scripts/indexgen/canonical.py`) operates on raw bytes:

1. Cloudflare `data-cfemail` spans/links are decoded (first byte is the XOR key)
   back to plain text or `mailto:` links.
2. `<script>` elements containing `cdn-cgi`, `cloudflare`, `__CF$cv$params` or
   `cf-beacon` are removed (OASIS responses sometimes carry a Cloudflare
   Insights beacon); other scripts are kept.
3. All whitespace before `</body>` becomes a single CRLF.

SHA-256 of the canonical bytes is pinned per version in
`src/mqtt_spec_mcp/versions.py`. Two fetches that differed in raw bytes (with and
without the beacon) produced identical canonical hashes:

| Version | Canonical SHA-256 |
| --- | --- |
| 3.1.1 | `82bbab8153f69854f240dfccb0bcd9457eb058feb268a9b51ab3db43a5ee8dc4` |
| 5.0 | `623cd5b41e73c7518cb9ccce235e45b897af9e5a891d3534309f85bd118a680c` |

`--allow-source-mismatch` writes the actual hash into the index metadata, so the
loader refuses that index until the pin is updated deliberately.

3.1.1 is pinned to MQTT Version 3.1.1 Plus Errata 01 (OASIS Standard Incorporating
Approved Errata 01, 10 December 2015), not the original 2014 HTML (canonical hash
`93167b6b…`). Errata 01 makes one change, "not substantive" per OASIS: the
Remaining Length decoding pseudocode in section 2.2.3 checks the range before
updating the multiplier, because the 2014 order rejects valid four-byte lengths.
Indexed, the two editions are identical except that block: the same 162 sections,
141 requirement labels, packets, return codes and terms. The envelope's
`specification` stays "MQTT Version 3.1.1"; results link the errata edition.

## Parsing

- Body parsing starts at the first numbered heading `1 …` and stops at the first
  `AppendixHeading1` paragraph, in **both** versions (not only 3.1.1), so appendix
  text is never attributed to section 7.x. Appendix blocks are captured
  separately and used only for label reconciliation (below).
- Tracked changes: the 3.1.1 Plus Errata 01 HTML is the whole specification with
  the correction marked up, inserted text in `<ins>` and removed text in `<del>`
  (shown struck through). `<del>` elements are dropped before parsing and `<ins>`
  text is kept, so the index holds the corrected text once. The 5.0 index is
  unchanged by this rule (regenerated byte for byte).
- Word `MsoCommentText` paragraphs are body text in these publications (3.1.1
  section 3.1.2.4 carries `MQTT-3.1.2-4` and `MQTT-3.1.2-5` in them), so they are
  kept. Table-of-contents, header and footer classes are skipped.
- Word list markers are detected from the `font:7.0pt` spacer span. Bullet glyphs
  are stripped; ordinal markers (`1.`, `a)`, `(i)`) are kept in the text because
  the numbering carries meaning.
- 3.1.1 headings that are not numbered (`Table 2.1 - …`, `Figure 3.1 - …`) become
  paragraphs, so the shared "caption directly before a table" rule applies.
- Cell text joins block-level children with spaces; rowspan/colspan values are
  copied into every covered grid position; empty rows are dropped.
- Glossary terms: a paragraph (not list item) that starts with a short name of at
  most five words, beginning with a capital letter, followed by `:` starts a term;
  following blocks belong to it until the next term. This handles both the inline
  (`Name: definition`) and heading (`Name:` then paragraphs) forms, which in fact
  appear mixed in both publications.
- Fixed-header flags: a 4-bit string when all four bit cells are `0`/`1`;
  otherwise `"<flags column> (Bit 3: …, Bit 2: …, Bit 1: …, Bit 0: …)"` keeping
  the printed cells (3.1.1 prints footnote markers such as `DUP1`).
- Property sections: `2.2.2.2` plus every chapter-3 section whose title equals the
  property name after normalization, tolerating singular/plural spelling (the
  publication titles 3.2.2.3.12 "Subscription Identifiers Available").
- Packet sections are the chapter-3 level-2 sections whose title starts with the
  packet name (`3.1 CONNECT – …`).

### MQTT 5.0 requirement reconciliation

The 5.0 body prints 250 distinct bracketed labels, while the completeness gate
requires 252. Appendix B (the publication's own list of normative statements)
names two labels the body does not print recognizably: `MQTT-3.2.2-8` (printed as
`T-3.2.2-8]` in 3.2.2.2) and `MQTT-4.2.0-1` (printed as `MQTT-4.2-1` in 4.2). For
each Appendix B label missing from the body, the generator finds the body block
containing the Appendix B statement text and indexes the label there; it fails if
no such block exists. This is a no-op for 3.1.1, whose Appendix B labels all
appear in the body.

## Search

- BM25F over three fields: title (weight 5, b=0.3), ancestor titles ("path",
  weight 1, tf capped at 1) and body (b=0.5), k1=1.6, one saturation per term.
  This rewards covering several query terms over repeating one title word.
- Tokens are lowercase alphanumeric runs after NFKC/dash normalization, stemmed
  with the Porter (1980) algorithm (`src/mqtt_spec_mcp/stemmer.py`, checked against
  the paper's published examples), so "closes"/"closed"/"closing" match.
  Exceptions keep MQTT concepts apart: "connection(s)" is not reduced to
  "connect", which would match every CONNECT packet section title.
- Stopwords are removed before stemming: English function words plus question
  fillers ("happen", "explain", "mean", ...). "will" is not a stopword because
  Will Message, Will Flag and Will Delay are MQTT terms.
- Boosts: section id = 1000 (also "Section 3.1", "§3.1", "3.1."); requirement
  label in its home section = 600, in another section that lists it = 400; title
  equal = 300; title contains the query = 100; body contains the whole phrase =
  10; each adjacent pair of query terms (ignoring stopwords between them) in the
  title = 6, in the body = 2; a 0x hex identifier present = 8; +0.25 per
  normative label (max 4 labels); query terms named only by ancestor headings get
  0.5 × idf each, unsaturated ("3.9.3 Payload" sits under "SUBACK"). The own
  title is already weighted inside BM25F; a separate own-title bonus was tried
  and rejected because it ranked single-property sections above 4.10.1 for
  multi-concept request/response questions.
  Requirement-label and section-id queries skip BM25 (their digits are noise).
- These settings were chosen by measuring the 120-case retrieval benchmark, a
  separate set of 45 practitioner queries, and title self-retrieval together,
  taking values from the flat middle of the range rather than the single best.
- Search returns an evidence pack, as Markdown, instead of a JSON list of ranked
  results with snippets. Ranking is unchanged; the pack takes the 8 best-ranked
  sections, splits their bodies into sentences (each line, split after `.`, `;`,
  `!`, `?`), scores every sentence by the idf of the distinct query terms it
  contains (+5 for the whole query phrase, +3 for any sentence of the best-ranked
  section), doubles the score of a normative sentence (MUST, SHOULD, MAY, REQUIRED,
  SHALL or a requirement label), divides it by 1 + 0.15 × the section's rank, and
  adds sentences best first, each followed by its next and previous
  sentence, while the excerpts and their `## <id> <title>` headings fit 5,500
  characters. Sections appear in rank order, sentences in document order with
  ` ... ` between non-adjacent ones; a sentence of 30 or more characters already
  shown in a higher-ranked section is skipped (the CONNECT and CONNACK copies of a
  property share most of their text). Requirement-label queries show the
  requirement in its home section (1,600 characters) and the sections that list it
  (400 each): 3.1.1 quotes the indexed excerpt, 5.0 windows the printed label,
  falling back to the excerpt for the two labels reconciled from Appendix B.
  Section-id queries show that section from its start (3,000 characters).
- Why: in the first full agent runs most facts the `mcp` condition missed were in
  a relevant section the model never read, usually ranked just below the results
  shown, and each extra model call re-sends about 2,700 tokens of prompt and tool
  definitions. Replaying the model's own first searches, the previous response
  (1,600-character first snippet, 640 for each later result, a `parent_context`)
  held 0.80 of the answer-key facts in about 1,190 `o200k_base` tokens; the pack
  holds 0.88 in about 1,550, more than that response plus a get of its best
  section (0.85). Earlier steps on the same path: query-focused passages instead
  of one window per snippet (0.67 to 0.72 at the same size), 640-character later
  snippets (0.77), a fourth result (0.81). Doubling normative sentences (0.89)
  and the best section's base score (0.90, same size) came after: answer keys turn
  on rules, and the base score fills a list of conditions in the best section
  (Receive Maximum's quota rules, say) before single-term matches in sections
  ranked lower. Re-ranking by best single-sentence coverage, title
  diversification, attaching the packet's Actions section and a budget scaled by
  the number of query terms were measured and rejected (at most +0.01 at the same
  size, or lower retrieval metrics).
- List context: a chosen sentence in a list brings the list's lead-in (the
  sentence ending with `:` before it) and, when lead-in and items total at most
  1,200 characters, the whole list. Why: of the facts the pack cut from a section
  it showed, 7 of 13 were list items, usually without their lead-in ("Each time a
  PUBREC packet is received with a Return Code of 0x80 or greater" means nothing
  without "The send quota is incremented by 1:"). At the same size first-search
  coverage moved only from 0.915 to 0.917 (5.0 edge +2.5 points and synthesis +1.3,
  3.1.1 applied -1.1 and edge -1.7): a whole list displaces other sentences. It is
  kept because a list shown whole is read correctly; a 600-character limit was
  worse (0.910).
- Related requirements: after the pack, up to 700 characters of labelled
  requirement sentences from the sections ranked 9th to 40th that are not in the
  pack, each sharing at least two distinct query terms, scored by the idf of those
  terms with no rank discount, best first. Why: across four same-time runs the
  facts MCP missed most consistently (in at least two of three runs while grep got
  them) were rules stated in a short section or in a sentence that does not repeat
  the question's main term, so the section ranks low: PINGREQ Actions (rank 17 for
  a keep-alive question), DISCONNECT only after a successful CONNACK, 3.1.1's close
  on a protocol violation. On the model's first searches the pack held 0.903 of
  the answer-key facts; with related requirements 0.917, for about 180 more
  `o200k_base` tokens per search, against 0.908 for the same 700 characters added
  to the pack itself. At equal total size (a 4,800-character pack plus 700) there
  is no gain, so this is the most efficient use of extra characters, not a free
  one. Drawing the pack itself from 12, 16 or 24 sections changed nothing. An
  explicit `limit` turns related requirements off.
- Everyday spellings are rewritten into the specifications' terms before matching
  (not in requirement-label or section-id queries): `keepalive`/`keep-alive` to Keep
  Alive, `LWT`/`last will (and testament)` to Will, `broker` to Server, `QoS0` to
  QoS 0, `client id` to ClientID, `kick` to disconnect. Why: `keepalive` (one word)
  matched only a reason code table row (no result at all in 3.1.1), and `LWT` and
  `broker` occur in neither specification; questions from practitioners use them.
  Rewriting to "Will Message" or adding "Client Identifier" was tried and dropped:
  those title words pulled the payload field sections above the rules. On the 220
  corpus queries Recall@1 rose from 0.80 to 0.81 and MRR from 0.87 to 0.88 (five
  queries gained the right first section, one moved it to second); 26 of 1,569
  benchmark searches by the model contained such words, and first-search coverage
  was unchanged.
- Multi-part queries: `;` separates the parts of a question (at most four; more
  are joined to the fourth). Each part is ranked and excerpted on its own share of
  9,000 characters (at least 2,500), sharing one set of sentences already shown; a
  section chosen by several parts appears once with the union of their sentences,
  in the order the parts first choose sections. Related requirements use all the
  parts' terms. Why: hard questions have several parts, but one keyword query makes
  the pack pick sentences that share its words, so rules that answer the other
  parts in their own words are cut. Of the facts `mcp` never saw in 1,200 runs, 37
  of 53 were in a section the pack showed; `grep` mostly never looked (29 of 53) or
  saw only matching lines (16). In the 150 hard-question searches where the model
  searched one version two or more times, its first search held 0.827 of the
  answer-key facts in 1,600 `o200k_base` tokens; its searches joined as one
  multi-part query held 0.965 in 2,450 tokens, against 0.975 in 3,540 tokens plus
  1.19 more model calls when made separately. Totals of 5,500 and 7,000 characters
  held 0.897 and 0.941. The model had already used `;` this way unprompted in 9 of
  2,134 searches. A requirement-label or section-id part shows what a search for it
  alone would. In the paired run that followed (102 hard cases, two epochs) the
  model split 87 of 255 searches, needed fewer follow-up calls, and `mcp` led
  `grep` by 1.05 points (v8: 0.39) with 20% fewer tokens (v8: 13%); neither
  quality difference is significant, and the gain was not concentrated in the runs
  that split. On lookup and normative cases it split 10 of 66 searches and scored
  as v8 did.
- The pack ends with the next step: state each rule in the excerpts that bears on
  the question, with its MUST/SHOULD/MAY and conditions, and cite its section; if
  a needed rule is missing, get one listed section; do not search this version
  again for this question (to compare versions, search the other one once). The
  version-specific wording came after 11 of 60 comparison runs consulted only one
  version (quality 0.80 to 0.88, against 0.92 to 0.97 with both). With no match
  it says nothing matched in this version, that this is not proof of absence, and
  that it says nothing about any other version.
- The tools advertise only the parameters agents used in 803 benchmark runs
  (`outline` 7 calls, search's optional parameters 9 uses in 886 searches): outline
  `parent`; search `query`; get `section`, `cursor`; lookup `kind`, `query`,
  `packet`. The others (`depth`, `chapter`, `limit`, `normative_only`,
  `include_subsections`, `max_chars`) are still accepted. Descriptions and the
  server instructions are short, keeping the version-safety rules. The advertised
  schemas also leave out what the argument models enforce anyway: the `version`
  enum has no description, optional strings are plain `string` (null is still
  accepted) and non-empty checks are not advertised. Together the model-visible
  tool definitions and instructions fell from 1,222 to 531 `o200k_base` tokens per
  call (556 after the multi-part guidance); the scope sentence in every result is
  shorter too.
- The server instructions tell the agent to consult the tools before answering (in
  the first full run 4 of 120 MCP 5.0 runs answered from memory and scored 0.59).

## Section resolution

- Accepted reference forms: `3.1.2.4`, `3.1.2.4.`, `Section 3.1.2.4`, `§3.1.2.4`,
  `Chapter 4`, and `"<id> <title>"` with a space, `-`, `–` or `:` between them.
- `"<id> <title>"` accepts the title when its words equal the section title's
  words, or either is a whole-word prefix of the other (`3.1 CONNECT` resolves to
  `3.1 CONNECT – Connection Request`); anything else fails with `title does not
  match`. Titles compare word by word, ignoring punctuation, so 5.0's heading
  "Message Expiry Interval\`" (a stray backtick in the publication) resolves.
- Conflicting-version guard: `MQTT 5`, `MQTT 5.0`, `MQTT5.0`, `MQTT-5`, `MQTT v5.0`,
  `MQTT version: 5.0`, `MQTT Version 5.0` mean 5.0; `MQTT 3.1.1` means 3.1.1;
  `MQTT 3.1` (unsupported) is rejected for both; a bare `MQTT 3` is treated as 3.x
  (allowed for 3.1.1; the error for 5.0 suggests version='3.1.1'). Requirement
  labels (`MQTT-3.1.2-4`, `MQTT-3-8.3-4`) never trigger the guard, and neither does
  an exact reference to a section of the selected version whose title names a
  version (5.0's `1.8.1 MQTT v3.1.1`).

## Get and cursors

- Fragments are at most 600 characters and at most half of the page's content
  room. Pages hold whole fragments, so a long fragment after a short one would
  otherwise leave most of a small page empty. Room is reserved for the
  "(continued)" header, banner and a footer containing the longest possible
  cursor (position 10^7), so every page fits.
- Long paragraphs split at the last sentence end (`.`, `;`, `:`, `?`, `!`, `)`
  followed by a space) that leaves the piece at least half full, else at the last
  word boundary.
- Subsection headings use `#` × (1 + level difference), capped at 6.
- A section without its own blocks renders a placeholder: "its subsections
  follow" when they are included, otherwise a pointer to `include_subsections`
  or `mqtt_spec_outline`.
- Cursor (format 2) = URL-safe base64 (no padding) of
  `2,<version>,<first 12 hex of the source SHA-256>,<section>,<0|1>,<max_chars>,<position>`,
  about 50 characters. The 12-hex prefix distinguishes pinned publications while
  keeping cursors short enough for agents to copy exactly. Unsigned: cursors carry
  no secrets and the server validates every field. Cursors over 128 characters or
  in any other format are rejected as invalid.

## Lookup

- Return-code and packet `code` fields are hex strings (`0x00`).
- Lookup results carry the spec text that answers about the entity, so a lookup
  rarely needs a follow-up get: a packet's `summary` (its section's first 600
  characters), the prose of its fixed header section as `fixed_header` (400;
  DISCONNECT's reserved-bits rule with 0x81), `remaining_length` where the fixed
  header figure fixes it, and its Actions or Response sections as `actions` (600
  each: PINGREQ's "Server MUST send a PINGRESP" is a one-sentence section that
  multi-term searches rank low); a property's `details` (excerpts of 700 characters with
  their requirement labels); and for at most three reason codes, and for return
  codes, the row of each packet's own code table as `meanings` (with `sent_by`
  where the table has that column). In the evidence-pack benchmark runs that used
  only lookups, the results held 0.76 of the answer-key facts; with this text they
  hold 0.88, for about 460 more characters per lookup.
- A single property result always has `details`: with a packet filter, the
  sections in that packet's subtree; without one, every defining section except
  the 2.2.2.2 table when there are at most three, else none (User Property and
  Reason String are defined in 15 and 10 sections).
- `return_code` takes an optional packet filter, which must resolve to CONNACK or
  SUBACK (by name, number, or "connack packet"). Without it, a value or name returns
  the matches of both packets, each naming its packet (0x00 to 0x02 exist in both),
  and a query naming CONNACK or SUBACK lists that packet's codes. In the
  evidence-pack runs 19 of the 25 MCP tool errors were 3.1.1 return-code lookups
  without a packet filter or with the packet as the query, each costing a call.
- A `reason_code` query that is a packet name ("CONNECT") is answered with an error
  pointing to `kind=packet`, instead of substring-matching reason code names such
  as "Normal disconnection".
- Requirement labels match with or without brackets, the `MQTT-` prefix, or
  trailing punctuation (`3.1.2-4`, `[MQTT-3.1.2-4].`).
- Numeric queries are limited to 9 decimal / 8 hex digits; longer digit strings
  are ordinary misses.

## Benchmark

- The corpus covers both versions: 120 MQTT 5.0 cases, 60 MQTT 3.1.1 cases (a
  half-size set with the same category proportions) and 20 comparison cases. Each
  case has `version` "3.1.1", "5.0" or "both". In comparison cases every fact,
  forbidden claim and lookup names its version, and section references are
  version-qualified (`3.1.1:3.1.2.4`), because the same number often means
  different things in the two versions. Answers cite bare section numbers, so a
  comparison citation group is satisfied by its number in either version.
- Case schema additions beyond the required fields: each fact and forbidden claim
  names the `section` that grounds it, and each case has a `reference_answer`.
  The validator requires every fact to have one regex alternative matching its
  section's text in its version, every case's reference answer to pass the scorer
  within its word limit, no 8-word run of a prompt or search query to be copied
  from either spec, lookups/queries not to reuse unit-test scenarios, comparison
  prompts to name both versions, and each single-version set to cover all seven
  chapters and every control packet of its version.
- Retrieval metrics: Recall@k = mean(|relevant ∩ top-k| / min(|relevant|, k));
  hit rate = any relevant section in the top 5; MRR on the first relevant hit.
  Each case's reference query is ranked against every version it is about, so a
  comparison case contributes one query per version; metrics are reported overall
  and per version.
- Scorer negation (scorer 1.1.0): an affirmed fact is not credited if a negation
  cue appears in the 48 characters before the match within the same clause; a
  negated fact requires a cue there or inside the match; a forbidden claim is a
  violation only when no cue appears before it or inside it. (1.0.0 ignored cues
  inside forbidden matches, which flagged correct answers such as "should not
  retransmit"; found by the answer-key review.) Section citations ignore numbers
  directly preceded by `MQTT`, `v` or `version`; citing a descendant of a cited
  section satisfies the group. Scorer 1.2.0 accepts version-qualified citation
  entries.
- Scorer 1.3.0 and key windows, from the pilot run, where correct answers failed:
  answers are normalized before matching. Markdown emphasis and code markers are
  removed ("it **SHOULD NOT** disconnect"), a heading-only line is joined to the
  paragraph it introduces with ": ", and curly apostrophes are folded. Negation is
  scoped to the clause: parenthetical asides and earlier ", and"/", but" clauses
  do not negate what follows, and an upper bound ("must not exceed 65535", "no
  more than 3") states the bound instead of negating it. Sentence-scoped windows
  in the answer keys also accept dots inside numbers and e.g./i.e., so an inline
  citation ("per section 4.8, ...") does not end a match. Lookup cases accept the
  packet-specific section or the summary table (2.1.x, 2.2.2.2, 2.4) in one
  citation group, since either states the requested facts.
- Scorer 1.3.1, from the 3.1.1 key review: version numbers are not citations.
  "5.0" is never a section number in either specification, and a bare "3.1.1" is
  the version label (231 of 231 bare uses in the first full run), so it counts as
  section 3.1.1 only after "section", "sec." or "§" (also within a list such as
  "sections 3.1 and 3.1.1"). Before, any "3.1.1" satisfied citation groups for
  3.1 or chapter 3, and any "5.0" satisfied groups for chapter 5. The check for a
  pattern that spells out its own negation now matches whole words only (also after
  an escape such as `\b`), so `in[- ]?flight` or "another" no longer switch off the
  self-negation check.
- Scorer 1.3.2, from the evidence-pack runs: a spaced dash (an em or en dash,
  which normalization folds to `-`) ends a clause, so "it is not a failure - the
  publish was accepted" credits "accepted". It changed 4 of 3,612 stored answers,
  all to correct credit.
- All four agent conditions are implemented as in-process tools with identical
  loop and limits (12 tool calls), and each reaches the same material: the
  specification(s) the case is about. `full_spec` and `grep` get that text; `mcp`
  gets this server's real tool schemas and instructions, served by an instance
  loaded with only the case's version(s), so a call for any other version fails
  rather than leaking it. Comparison cases load both versions everywhere.
- The base prompt covers both versions and tells the model not to transfer rules
  between them. Single-version questions are sent prefixed with `[MQTT 3.1.1]` or
  `[MQTT 5.0]`, as a user of a multi-version tool would label them; comparison
  questions name both versions themselves.
- Run records carry four hashes: shared instructions (`base`), the condition's
  prompt (`prompt`), the reference material it can reach (`reference`: the spec
  text for `full_spec`/`grep`; for `mcp`, the tool schemas, instructions, the source of
  the server modules and the index files),
  and the question (`case`: id, version, prompt, word limit). The report requires
  one `base`, one `prompt`/`reference` per condition and one `case` hash per case,
  so a single condition can be re-run after a server change and compared with
  stored results for the others. Answer keys are excluded from the hashes because
  `--rescore` re-applies the current keys to stored answers.
- Resumed runs append retries after failed attempts; the report keeps one record
  per (model, condition, case, epoch): the last successful one, else the last
  failure.
- Conditions are compared only within runs made together. On 2026-10-19 the
  unchanged `grep` condition scored 2.7 points lower in an evening pass than in a
  midday one (paired 95% CI 1.0 to 4.3; fact recall 0.981 against 0.951), while two
  `mcp` passes run side by side that evening agreed within 0.2 points. Re-running one
  condition later therefore measures the model's drift as well as the change. The
  report's `--epoch` option restricts it to the runs of one pass; a re-run of one
  condition should be followed by a pass of the conditions it is compared with.
- Answer keys are checked against stored answers (blind to condition) and those
  answers are then rescored, so results on answers a key check has already seen
  are slightly optimistic for both conditions. Headline results use a pass whose
  answers no key check had seen; across three checks, keys fitted to earlier
  answers raised the scores of later, unseen answers about equally for `mcp` and
  `grep`.
- Copilot SDK runner: `CopilotClient(mode="empty")`, built-in tools disabled via
  `available_tools` (custom tools only, or none), system message in `replace`
  mode, infinite sessions off, one fresh session per run, `--concurrency` sessions
  at a time. Token counts come from the runtime's per-call usage events:
  `input_tokens` includes cache reads and writes (observed: input = cache read +
  cache write + uncached), and `cost` is the runtime's premium-request units, one
  per model call for Claude Sonnet 5, so multi-call conditions cost more per run.
- Inspect AI runner: a per-sample `react` agent without the submit tool, so the
  loop ends when the model answers, matching the Copilot loop. Conditions are
  separate tasks (`mqtt_none`, `mqtt_full_spec`, `mqtt_grep`, `mqtt_mcp`, or
  `mqtt_reference -T condition=...`), filtered with `-T versions=...`; the case
  order is seeded via dataset shuffling.
